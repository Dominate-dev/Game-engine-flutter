## Project Overview

A Flutter **module** (`project_type: module`), not a standalone app and not a
native Android project. Built for **add-to-app** embedding into existing native
Android and iOS hosts.

Pub workspace with three packages:

| Package | Responsibility |
|---|---|
| root (`.`) | Module entry point + `HomeLauncherPage`, a development harness |
| `packages/coreapp` | Shared infrastructure. No game logic. |
| `packages/play_game` | The "play" game plugin. Depends only on `coreapp`. |

`.android/` and `.ios/` are **generated and gitignored** — regenerated by
`flutter clean`. `.android/app` is a throwaway dev runner, never a release target.

Main technologies: Riverpod, Dio, `signalr_core`, `shared_preferences`,
`connectivity_plus` + `internet_connection_checker_plus`, `pointycastle` +
`asn1lib`, `just_audio`, `lottie`, `flutter_svg`, `chucker_flutter`.

## Architecture — VERIFIED

```
UI (BaseState)
  → Riverpod Notifier / provider
    → UseCase
      → Repository (abstract, domain/)
        → RepositoryImpl (data/, wrapped in BaseRepository.guard)
          → RemoteDataSource
            → ApiClient (Dio)  |  SignalRService (hub)
```

Dependency direction correct: `coreapp` has **0** references to `play_game`;
`play_game` has 3 to `coreapp`. Zero `catch` in feature code — the `guard()`
exception boundary holds.

### GameController family — VERIFIED

| File | Lines | Structure |
|---|---|---|
| `game_controller.dart` | 628 | host class |
| `round_screen_handler.dart` | 268 | `part of` + `extension RoundScreenHandler` |
| `lobby_screen_handler.dart` | 155 | `part of` + `extension LobbyScreenHandler` |
| `waiting_screen_handler.dart` | 47 | `part of` + `extension WaitingScreenHandler` |
| `game_controller_screen.dart` | 245 | screen |
| `game_session_reducer.dart` | 163 | pure merge helpers |

The `part` directive is **load-bearing** — the extensions reach into roughly
eleven private members of `GameController` (`_didJoinRandom`, `_gameFromData`,
`_refreshLobby`, `_routeByStatus`, `_emoteIsMine`, `_findPlayers`, `_goToRound`,
`_meEmoteTimer`, `_opponentEmoteTimer`, `_opponentCardPulseAfter`,
`_readyButtonPulseAfter`).

### SignalR — VERIFIED

18 client→server methods, 35 server→client events, 9 event-group constants in
`PlayGameHubEvents`. Transport is WebSockets with `skipNegotiation: true` plus a
custom `SignalRHttpClient` that injects native headers on the upgrade.

`GameController.onRecovered()` invokes `CheckPlayerGame`, so the
`ConnectionRecoveryController` mechanism is **live**.

> **EXTERNAL VERIFICATION REQUIRED.** An in-code comment states the server
> rejects `?access_token=` with WebSocket close 1002, which is the stated reason
> for `skipNegotiation`. That has not been confirmed against a running backend
> and may describe a server that no longer behaves that way.

**Proof the handler rename changed no logic — VERIFIED.** Normalising `_s` back
to `state` across both diffs yields evenly-paired added/removed lines; the only
text-differing lines are the four belonging to the approved `const` fix.

**The `const` fix is a separate case — INFERRED, not VERIFIED.**
`RoundLottieDialog` is a `ConsumerStatefulWidget`, so `const` canonicalizes the
instance and every call site receives the same object. Each `showDialog` still
builds its own Element and State, so the practical impact is judged nil — but
this is a semantic change rather than a purely textual one, and it was not
exercised at runtime.

**What Option C did not do — VERIFIED.** It fixed the analyzer problem by using
a legal access path rather than silencing a diagnostic. It did **not** decouple
the handlers: they remain welded to the Notifier and cannot be constructed or
tested in isolation. **A4 Option D remains open.**

### Identity — BLOCKED

| ID | Sev | Finding | Label |
|---|---|---|---|
| **S9** | High | `isCurrentUser`, `isLocalPlayerLeft` and `_emoteIsMine` reduce to *"if not the seated opponent, it is me"*. `_findPlayers` can legitimately return `opponent: null`, in which case **every** id resolves to the local user. | **VERIFIED** (code behaviour) |
| **S9a** | High | With no opponent seated, any `PlayerLeft` reports the local user as leaving, and `GameControllerScreen` pops the game screen on that result — so the local player could be ejected from their own game. | **VERIFIED** (code path) / **INFERRED** (that the hub can deliver such an event before seats resolve) |
| **S9b** | Medium | With no identity match, `_findPlayers` falls back to positional seating (`players[0]` = me). | **VERIFIED** |

**Five questions block any identity fix — EXTERNAL VERIFICATION REQUIRED:**

1. Does the hub always send `userId` on players, or sometimes only a GUID `id`?
2. Is `PlayerLeft.playerId` a game-player id or an account id?
3. Is `PlayerEmoted.userId` the account id? *(a comment says so — not proof)*
4. Is `CreatedGame.currentTurn` a game-player id or an account id?
5. Is prefs `user_id` in the same namespace as either hub id?

**No identity behaviour was changed.** Six characterization tests pin the
current behaviour without endorsing it.
